Bozza tecnica

Principi non negoziabili

1 · Il ledger è la verità. Nessun saldo memorizzato "a mano": ogni saldo è la somma di movimenti immutabili. Si scrive append-only, si legge per proiezione.
2 · Denaro fuori solo ai due estremi. Fiat entra alla ricarica, esce al settlement. In mezzo i TIN non toccano circuiti di pagamento.
3 · Ogni transazione è atomica e idempotente. Doppio tap, retry di rete o QR riusato non devono mai duplicare un movimento.
4 · Solo smartphone. Nessun hardware esterno: il telefono cliente e quello del validatore sono gli unici endpoint.

Ledger — modello dati

Doppia partita minimale: ogni evento sposta valore da un conto a un altro. Tre tipi di conto: user organizer system (issuance, fee, breakage).

// entry immutabile — importi in centesimi di TIN (interi, mai float) Entry { id: uuid, ts: timestamp, type: "topup" | "spend" | "gift" | "settlement" | "fee", from_account: id, // system:issuance per topup to_account: id, amount_tin: int, // es. 1450 = 14,50 TIN idempotency_key: string, // unico: no doppie scritture ref: { event_id, pos_id, nonce, fx_quote_id? } } // saldo = Σ(to==acct) − Σ(from==acct), mai un campo mutabile

Perché centesimi interi: i float (0.1+0.2≠0.3) corrompono i saldi. Tutto in int, formattazione solo in UI.

Transfer atomico + idempotenza

transfer(from, to, amount, idempotency_key): begin tx if exists(idempotency_key): return stored_result // retry-safe if balance(from) < amount: abort "INSUFFICIENT" // il chiamante ricarica e ritenta insert Entry{from, to, amount, idempotency_key} commit // atomico push(from.device); push(to.device)

Cambio valuta (FX)

Il cambio agisce solo alla ricarica. Il tasso viene bloccato per una finestra breve (quote lock) così il prezzo mostrato è quello addebitato.

POST /topup/quote { currency: "USD", tin: 5000 } → { quote_id, rate: 1.08, spread: 0.01, fiat_total: 5454, // $54,54 in centesimi USD expires_at: ts+60s } POST /topup/confirm { quote_id, payment_token } // server ri-verifica quote non scaduta, incassa via PSP, // poi transfer(system:issuance → user, tin) al tasso bloccato

Se il quote scade prima del confirm → nuovo preventivo, mai addebito a tasso vecchio. I TIN accreditati sono sempre l'importo in TIN richiesto (il rischio FX è già nel fiat incassato).

Spesa — intent di incasso (Variante A)

// 1. validatore crea l'intent POST /charge/intent { pos_id, amount_tin: 1450 } → { intent_id, nonce, expires_at: ts+90s } // → QR // 2. cliente risolve e conferma POST /charge/confirm { intent_id, biometric_ok: true } // server: valida nonce+TTL, soglia anti-frode, saldo; // transfer(user → organizer, amount) idempotente su intent_id → { status: "ok", new_balance } // push a cliente e cassa

L'intent_id è la chiave di idempotenza: un QR vale una sola transazione. TTL breve + nonce monouso impediscono replay.

Spesa offline

Nell'MVP. Modello a tetto pre-autorizzato + voucher firmati dal device; riconciliazione al ritorno della rete.

MeccanismoCome
Tetto offlineAll'ingresso l'app riserva una quota del saldo (es. 5000 TIN-cent) spendibile senza rete; oltre serve online
Voucher firmatoOgni pagamento offline = payload firmato dalla chiave del device, con nonce progressivo per-device
Verifica cassaIl validatore verifica la firma localmente (chiave pubblica sincronizzata a inizio turno), senza server
RiconciliazioneAl ripristino rete: i voucher salgono, il ledger li applica in ordine di nonce, detrae dal saldo reale

Rischio residuo: un device compromesso può spendere due volte entro il tetto prima della sync. Si contiene con tetti bassi + nonce monotono per-device, non si azzera. Partenza consigliata: tetti bassi, alzati con i dati.

PSP, custodia fondi e KYB

AspettoApproccio
Incasso ricarichePaymentIntent PSP; carta, Apple/Google Pay, SEPA. I fondi restano in custodia, non toccano l'organizzatore
CustodiaConto di salvaguardia presso il PSP; i TIN sono la rappresentazione contabile dei fondi custoditi
Payout organizzatoreAccount connesso (es. Connect); payout bloccato finché KYB azienda non è completo
Fee3% trattenuto al payout; registrato come Entry di tipo fee verso system:fee
Confine EMIFinché è closed-loop, esenzione rete limitata. La Fase 3 (P2P a pagamento / cash-out cliente) richiede partner EMI — scegliere fin da subito un PSP con quel percorso
